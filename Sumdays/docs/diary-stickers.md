# 일기 스티커

## 사용 흐름

일기 읽기 화면의 `스티커 꾸미기` 버튼(친구 일기는 `장난치기!`) → 보유 스티커 선택 → 끌어서 위치 조정 → 크기·회전 조정 → `붙이기` 순서다.
취소하면 수량은 바뀌지 않는다. 붙이기를 확인하면 해당 계정의 보유 수량에서 1개를 사용한다.
스티커 선택 창에서 상점의 스티커 탭으로 바로 이동할 수 있다.

- 로그인과 서버 연결이 필요하다. 내 일기는 공개 여부와 관계없이, 친구 일기는 공개된 경우에 사용할 수 있다.
- 일기 본문을 수정하는 중이거나 본문이 없으면 스티커 버튼을 숨긴다.
- 붙인 스티커를 누르거나 `붙인 스티커 관리`에서 선택해 수정한다.
- 붙인 스티커가 없어도 `스티커 꾸미기`(친구 일기는 `장난치기!`) 오른쪽에 `스티커 가리기` 버튼을 표시한다. 누르면 내 화면에서만 숨기고 `스티커 보이기`로 다시 표시할 수 있다. 저장된 스티커와 수량은 바뀌지 않으며, 새로고침이나 본문 수정 후에도 선택을 유지한다.
- 직접 붙인 스티커만 위치·크기·회전을 바꿀 수 있다. 붙인 사람과 일기 주인은 삭제할 수 있다.
- 수정은 추가 수량을 사용하지 않는다. 삭제 시 사용한 수량을 돌려주지 않는다.
- 한 일기에 최대 50개까지 붙일 수 있다. 스티커는 본문 위에 표시하며 사진 영역에는 표시하지 않는다.

## 저장과 권한

`DiaryStickerController`는 내 일기/친구 일기 화면에 공통으로 연결된다.
`StickerCanvasView`는 위치를 페이지 내부의 비율로 저장하고, 크기를 페이지 너비의 비율로 저장한다.
`StickerPageLayout`은 읽기/편집 화면의 최소 페이지 비율을 동일하게 유지한다.
본문 길이나 글꼴 크기가 달라지면 페이지에 대한 상대 위치를 유지하므로 특정 글자에 고정되는 방식은 아니다.

서버는 JWT의 사용자 ID로 요청자를 판단하고, 일기 소유자·날짜·공개 여부·양방향 ACCEPTED 친구 관계를 확인한다.
클라이언트에서 전달하는 작성자 ID는 사용하지 않는다. 비공개 전환/친구 해제 후 조회·신규 배치·수정을 거절한다.
일기 주인은 자기 일기에 있는 다른 사람의 스티커도 삭제할 수 있다.

배치 전에 아직 동기화되지 않은 내 일기는 기존 일기 동기화 API로 저장한다.
스티커는 Room 일기 행과 분리된 서버 `diary_stickers` 테이블에 저장되어 친구 화면에서도 조회된다.
일기 삭제 시 FK를 NULL로 바꾸고 조회에서 제외한다. 같은 날짜의 일기를 다시 만들어도 이전 스티커가 복원되지 않는다.

스티커 재고와 포인트는 기존 상점 구조대로 **기기 내 계정별 저장소**를 사용한다.
서버는 스티커 배치와 접근 권한을 관리하며 구매 재고/포인트를 검증하지 않는다.
따라서 구매 재고의 다른 기기 간 동기화나 변조 방지까지 보장하는 서버 지갑은 이번 구현에 포함되지 않는다.

## 수량 차감과 재시도

UUID 요청 ID, 최초 위치 정보, 수량 1개 차감을 SharedPreferences의 한 `commit`으로 기록한다.
서버는 UUID별 최초 요청 정보를 영수증처럼 보관해 같은 요청을 재전송해도 중복 배치하지 않는다.
응답을 받은 뒤 예약 기록을 지운다. 명확한 배치 거절만 수량을 한 번 돌려준다.
타임아웃/서버 오류/인증 만료처럼 결과가 불명확하면 예약을 유지하고 다음 새로고침에서 동일 ID로 확인한다.
이전 요청이 해결되기 전에는 다른 스티커를 새로 사용하지 않는다.
이미 저장된 요청은 스티커 삭제·일기 삭제·권한 철회 후에도 영수증을 돌려주어 잘못 환급하지 않는다.

화면을 닫거나 계정이 바뀌어도 전송 중인 예약 정리는 원래 계정 저장소에서 끝낸다.
날짜 또는 계정이 바뀌면 이전 요청 결과를 새 일기 화면에 적용하지 않는다.

## 서버 적용

`sumdays-backend/server.js` 시작 시 `db/migrations/001_diary_stickers.sql`을 적용한다.
`CREATE TABLE IF NOT EXISTS`만 실행하는 추가 마이그레이션이며 기존 테이블을 삭제하지 않는다.
기존 서버 배포 후 재시작하거나 서버의 DB 연결 설정을 확인한 환경에서 다음 명령을 실행한다.

```powershell
cd sumdays-backend
npm run migrate:stickers
```

기존 `db/initDB.js`는 전체 DB 초기화용이므로 운영 서버에 마이그레이션 대신 실행하면 안 된다.

스티커 요청에 HTML `Cannot GET /api/stickers/...`와 404가 반환되면 실행 중인 서버가 이전 코드를 사용하고 있는지 확인한다.
`node server.js`는 소스 변경을 자동으로 반영하지 않으므로 변경 후 서버를 재시작해야 한다.
인증 없이 스티커 API를 요청했을 때 JSON 401 응답이 오면 새 라우터가 연결된 상태다.

API는 `/api/stickers/:ownerId/:date`의 GET과 `/:id`의 PUT/PATCH/DELETE로 구성된다.
PUT은 `{stickerId,x,y,size,rotation}`, PATCH는 `{x,y,size,rotation}`을 받는다.
위치 범위는 0~1, 크기는 0.08~0.35, 회전은 -180~180도다.

## 검증

```powershell
# Sumdays 디렉터리: 기존 재고 회귀 테스트와 스티커 저장/좌표 단위 테스트
.\gradlew.bat -I gradle/fox-placement-tests.init.gradle :app:testDebugUnitTest --console=plain

# 별도 패키지로 실제 레이아웃/컨트롤러/편집기와 가짜 원격 저장소를 사용
.\gradlew.bat -I gradle/diary-sticker-device-tests.init.gradle :app:connectedDebugAndroidTest --console=plain

# 기본 패키지 APK 생성
.\gradlew.bat :app:assembleDebug --console=plain

# sumdays-backend 디렉터리: 실제 라우터/서비스와 메모리 SQL 대역으로 권한·트랜잭션 검증
npm run test:stickers
```

기기 검증은 `.inventorycheck` 패키지와 테스트 계정 101/202를 사용한다.
사용자 앱/일기 데이터와 실제 서버는 사용하지 않는다. 화면 캡처는 `app/build/outputs/connected_android_test_additional_output`에 수집한다.
테스트는 실제 MySQL 연결/운영 서버까지 포함하는 통합 검증은 아니다.
